Third pass on the existing Criminal Record Management System app. Add authentication and role-based access (admin, viewer). Do NOT change the four core tables (POLICE, CRIMINAL, COURT_RECORD, JAIL), the existing query SQL, or the theme. New tables and new routes only, plus guards on existing routes.

## Roles
- admin: full access. Everything the app does today, plus user management and the audit log.
- viewer: read-only. Can view Dashboard, Criminals, Police, Court Records, Jail, Case Board, Schema, profiles, and run the 10 saved queries in Query Explorer. Cannot create, edit, or delete anything. Cannot use the free-form SQL console. Cannot see the Users or Audit Log pages.
- No public sign-up. Only an admin can create accounts.

## Database (add to schema.sql, seed in seed.sql)
USERS(user_id INT PK AUTO_INCREMENT, username VARCHAR(50) UNIQUE NOT NULL, full_name VARCHAR(100) NOT NULL, password_hash VARCHAR(255) NOT NULL, role ENUM('admin','viewer') NOT NULL, is_active BOOLEAN NOT NULL DEFAULT TRUE, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, last_login TIMESTAMP NULL)
AUDIT_LOG(log_id INT PK AUTO_INCREMENT, user_id INT FK -> USERS.user_id ON DELETE SET NULL, username VARCHAR(50), action VARCHAR(20) [LOGIN, LOGOUT, LOGIN_FAILED, CREATE, UPDATE, DELETE, SQL_RUN], table_name VARCHAR(50), record_id VARCHAR(50), detail TEXT, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP)
- Seed two users: admin / viewer, with bcrypt hashes generated by a small script (server/scripts/create-user.js, usage: node create-user.js <username> <password> <role>). Default passwords go in the README as demo credentials with a note to change them. Never store plaintext passwords anywhere in code or seed.sql.

## Backend
- bcrypt (cost 12) for hashing. JWT in an httpOnly, SameSite=Lax cookie (Secure in production), 8 hour expiry. JWT secret from .env. No tokens in localStorage.
- Endpoints: POST /api/auth/login, POST /api/auth/logout, GET /api/auth/me, POST /api/auth/change-password (requires current password, min 8 chars).
- Admin only: GET/POST/PUT /api/users (create, edit name/role, activate/deactivate, reset password), GET /api/audit-log (paginated, filter by user, action, table, date range).
- Middleware: requireAuth on ALL /api routes except login. requireRole('admin') on every POST/PUT/DELETE for police, criminals, court-records, jail, and on POST /api/sql. Viewers get 403 with a clear JSON message.
- Field-level restriction on the server: for viewers, the API must strip police `number` and `address` from responses (return null). Do this in the query/serializer, not in the frontend. Admins get the full data.
- Safety rules: an admin cannot deactivate, demote, or delete themselves, and the last active admin can never be removed. Deactivated users are rejected at login and on every request (check is_active from the DB, not just the token).
- Rate limit POST /api/auth/login (5 failed attempts per 15 min per IP + username, then 429). Generic error "Invalid username or password" for both wrong user and wrong password. Constant-time compare via bcrypt even when the user does not exist.
- helmet, CORS restricted to the dev origin with credentials: true, reject state-changing requests that lack a custom header (X-Requested-With) as basic CSRF protection.
- Write to AUDIT_LOG on login, failed login, logout, every create/update/delete (with table and record id), and every SQL console run (store the query text). Never log passwords.
- All SQL parameterized, same as before.

## Frontend
- Login page at /login in the existing case-file theme: a "Criminal Records Bureau, Authorized Personnel Only" sign-in form on a paper sheet. Username, password (show/hide toggle), Sign in button. Inline error on failure. No demo credentials shown on the page. Disabled state and spinner while submitting.
- AuthContext with user + role, loaded via /api/auth/me on startup. ProtectedRoute redirects to /login when unauthenticated and returns to the intended page after login. Global fetch handler: 401 -> clear state and redirect to /login with a "Session expired" message; 403 -> toast "You do not have permission to do that."
- Role-based UI (remove, do not just disable):
  - Viewer: no Add / Edit / Delete buttons, no row action menus, no drawers for editing, no assign/reassign/remove on Court Records and Jail, no SQL console, no Users or Audit Log nav items. Profile pages are read-only.
  - Viewer: officer phone and address show as permanent REDACTED bars with no hover reveal (data is null from the server anyway). Admin keeps the hover/focus reveal.
  - Case Board: viewers can pan, zoom, drag and highlight (positions are local only), nothing that writes to the DB.
  - Hiding UI is cosmetic. The server is the real enforcement, as above.
- Top bar: user menu showing full name and a role stamp (ADMIN in red ink, VIEWER in blue ink), with Change password and Sign out.
- New admin-only pages:
  - /users: table of users (username, name, role, status, last login), Add user, Edit, Deactivate/Activate, Reset password. Show a warning when trying to touch your own account or the last admin.
  - /audit-log: dense table, filters, pagination, CSV export.
- Direct navigation to an admin-only URL as a viewer shows a "Restricted" page (typewriter heading, stamp), not a blank screen.
- Use the same components (DataTable, Drawer, ConfirmDialog, Toast). Same animation rules as before, including reduced motion. Login page gets the stamp-slam only on error.
- Sign out clears state and redirects to /login. Add an idle timeout: after 30 minutes of inactivity, sign out with a notice.
